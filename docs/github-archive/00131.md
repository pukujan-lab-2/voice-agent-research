# PR #131: Find a large site's forms by search and load only the one needed

A site with hundreds of forms can't keep every flow in memory, and the copilot had no way to find the right form from the page a visitor is on or from what they asked for.

## What changes

- A table in the business's Octo workspace, `copilot_site_map`, holds one row per page or form: path, title, keywords, the labels of a form's fields, and for a form its whole flow. A generated full-text column and an index make it searchable.
- `SiteMap` (`copilot-engine/src/site-map.ts`) finds by page path or by the visitor's words and returns a few small references; only `load` returns a flow, and it returns one. Every query is scoped by business.
- `GET /api/copilot/form?business=&path=|q=|id=` serves it; a business with no config gets 404.
- `npm run site-config -- map-put <business> <file.json>` indexes a site.
- Decision 0017 records the rule: the model sees a window of the form, and state lives in stores with a cap (Octo for what must survive a restart). `PROJECT.md` and `docs/scaling-limits.md` carry the limits.
- The stack check on `/api/desk` goes ahead if Octo can't be reached, since a stack list is a preference and not a secret.

## What stays unchanged

The widget still reads a form from the live page; the map is for callers with no page (the voice agent, phone calls) and for finding the page a visitor wants. Wiring the voice agent to it is a follow-up. Search has no synonyms of its own, so a business lists the words visitors use in `keywords`. Ingest and retrieval filters stay with the huge-sites work (#107).
