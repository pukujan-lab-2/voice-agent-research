# PR #130: Keep each business's copilot config in Octo and load it on demand

A business's pages, voice stacks and desk settings ride in the page and are sent with requests, so the server can't hold a call to the voice stacks that business allows, and a big site pays for its whole config on every load.

## What changes

- A table in Octo, `copilot_sites`, holds one config per business. `SiteConfigs` loads one on demand through a cache of 200 configs that each live 60 seconds, and validates a config before storing it (business id, size up to 256,000 characters, a sensible `voice` block).
- `GET /api/copilot/config?business=` returns a business's config; an unknown or odd id gets 404 or 400.
- `/api/desk` refuses (403) a voice stack outside the business's `voice.stacks` when the request names its business.
- `POST /api/session` refuses a business with no config, so a stranger can't open a key space of their own.
- A page can mount with `{ business, remote: true }` and take the rest from the server; what the page passes wins. The widget sends its business with desk requests.
- `npm run site-config -- put <business> <file.json>` stores a config using the Octo key the server uses.
- `docs/scaling-limits.md` records the limits.

## Before and after

| | Before | After |
|---|---|---|
| Where a business's config lives | in each page | in Octo, by business |
| Can the server enforce the allowed voice stacks | no | yes, for requests that name their business |
| Config held in server memory | none (it never had any) | at most 200 businesses for 60 seconds each |

## What stays unchanged

A page that passes its whole config still works. A desk request that doesn't name a business is checked as before. The config endpoint is public on purpose, so it must never hold a secret.
