# Issue #69: Offline scene suite stops at the voice scene, so a full run prints no summary

- State: closed (2026-11-01)
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/voice-agent-research/issues/69
- Labels: status:resolved

### Summary

The offline scene suite stops dead in its voice scene: the harness still fakes the browser's speech services, but calls have run on LiveKit since #61, so the fake is never consulted, no question is ever "spoken", and a 30 s wait throws. The run dies before printing any summary and before the phone layout scene, so the one command that checks the demo pages end to end reports nothing.

### Identity and Lineage

Leaf: this issue. Parent: none. Depends on: nothing (the cause arrived with #61, merged). Related: #65, whose "voice tests pass" acceptance was transferred here; #19, the other offline scene failure.

### Acceptance Criteria

- `npm run test:offline` runs to the end and prints its per-scene summary instead of throwing.
- A scene that cannot run headless says so, in the output, with the reason — it is not silently counted as a pass.
- The three phone "voice" checks in the layout scene either drive a real call or say what they actually measure.

### Boundaries and Next Action

In scope: `demo/live-site/tests/scenes.ts` and the local test server it starts. Out of scope: the widget, the engine and the speech stacks. Next action: detect the typing fallback after "Start voice call" and skip the voice scene with a printed reason.

### Symptoms

1. **The suite stops at the voice scene.** `npm run test:offline` on `main` prints `client voice: microphone: NotAllowedError`, then `page.waitForFunction: Timeout 30000ms exceeded` at `tests/scenes.ts:292`, and exits 1 with no summary line.
2. **The fake microphone is never used.** The scene replaces `SpeechRecognition` and `speechSynthesis`; the widget no longer reads either of them, so `window.__spoken` stays empty and every voice assertion has nothing to read.
3. **The layout scene never runs in a full run.** It comes after the voice scene, so a full run loses its checks even though the scene itself passes when named on the command line.

### Hypotheses

- **H1. The harness cannot drive a LiveKit call, so the voice scene can never pass headless.** Status: confirmed. Would confirm: the run logs the microphone refusal while the panel falls back to typing and `__spoken` stays empty. Would refute: a spoken question arriving without a microphone. Experiment: the 2026-11-01 run on merged `main` (`da521b8`) showed exactly that.
- **H2. A fake microphone plus a local LiveKit server in offline mode would let the voice scene run for real.** Status: unverified. Would confirm: with Chromium's fake media device and a server on `ws://127.0.0.1:7880`, the widget joins a room and the agent speaks the first question. Would refute: the widget failing to join without a hosted server. Experiment: not run.

### Evidence

- Run on `main` at `da521b8`, 2026-11-01, `npm run test:offline`: the tax scene passed its checks, then `== voice /clinic/book` logged `client voice: microphone: NotAllowedError | /clinic/book` and the process ended with the timeout above. No `live-site (offline): …` summary line was printed.
- `demo/live-site/widget/sdk.ts` takes the microphone first and, on `NotAllowedError`, calls `toText(...)`: "the call carries on by typing". That is the designed fallback for a visitor who refuses the microphone; in a headless browser it is the only path.
- `demo/live-site/tests/scenes.ts` still installs `FakeSR` as `SpeechRecognition`/`webkitSpeechRecognition` and stubs `speechSynthesis`; nothing in `widget/sdk.ts` reads either name.
- Counter-signal: the layout scene's three voice checks do pass today, because they measure the typing fallback's geometry rather than speech. They pass for a different reason than their names suggest.

### Honest Caveat

Nothing here is a product defect: a visitor with a microphone gets a voice call, and one without gets the typing fallback. The defect is in the test harness, and it hides the rest of the suite rather than breaking the demo.

### Problems vs Gaps

Problem: the suite cannot complete, so a full offline run cannot be used as merge evidence. Gap: no way to run a LiveKit call in the offline harness at all.

### Proposal

*(proposal)*
- Make the voice scene wait for either a spoken question or the typing fallback, and on the fallback print one `SKIP` line naming the reason, then continue to the next scene. Add the skip count to the summary so it is visible, not silent.
- Rename the layout scene's voice checks to say they measure the fallback's geometry, or gate them on a real call once one exists.
- Later, give the harness a real voice path: Chromium's fake media device plus a local LiveKit server started by the test server.
