LFM3-Audio-2B can run a call on this 8 GB M1 through llama.cpp, it streams audio out, and its card says tool calling works from speech. Live voice chat is English only. Nothing here has been run on this Mac yet; the numbers below are from the model card and Liquid's docs, read on 2026-11-01.

Leaf: #71. Parent: none. Depends on: [PR #61](https://github.com/Pukujan-lab/voice-agent-research/pull/61) (merged). Task WCP-0016, primary writer claude-code, branch `task/WCP-0016-lfm3-audio-stack` (not created yet).

**What the sources say (external evidence, not yet observed here)**

Sources: the [model card](https://huggingface.co/LiquidAI/LFM3-Audio-2B), the [GGUF card](https://huggingface.co/LiquidAI/LFM3-Audio-2B-GGUF), the [MLX card](https://huggingface.co/LiquidAI/LFM3-Audio-2B-MLX-4bit), Liquid's [audio capabilities](https://docs.liquid.ai/lfm/key-concepts/audio-capabilities) and [tool use](https://docs.liquid.ai/lfm/key-concepts/tool-use) pages, and the [llama.cpp v0.8.0 release notes](https://github.com/ggml-org/llama.cpp/releases/tag/v0.8.0).

1. **How it runs on this Mac.** llama.cpp v0.8.0 (build b11960) or newer has LFM3-Audio support. The GGUF repo has the model in five sizes; the card says `llama serve -hf LiquidAI/LFM3-Audio-2B-GGUF:Q4_K_M` serves a chat API and also takes real-time voice on a `/v1/realtime` WebSocket, with tool calls. The other routes do not fit or do not exist yet. The Transformers example loads the model in 32-bit floats on a CPU, about 8 GB for 2B weights, which is this Mac's whole memory. The MLX build (1.58 GB plus 0.15 GB codec) says MLX-VLM support "is in progress", with no release. The ONNX repo is 19.7 GB across its variants.
2. **Streaming.** Yes, both ways. The audio encoder is causal and prefills while the caller speaks; the codec decodes speech as it is generated (Transformers: `audio_streamer`; llama.cpp: `/v1/realtime` and `/tts`). The card claims a first token "as low as 50 ms" and the codec at 87 times real time on one Apple M4 Max CPU thread. Those are Liquid's figures on faster hardware than this M1; I have not measured either.
3. **Speech to text.** System prompt `Perform ASR in <language>.`, or `Perform ASR.` to let the model guess the language.
4. **Text to speech.** System prompt `Perform TTS in <language> using a <female|male> voice.`, 24 kHz output. The listed voices are Arabic, Danish, German, Greek, British and American English, Finnish, French, Hebrew, Italian, Japanese, Korean, Dutch, Polish, Portuguese, Spanish, Swedish, Turkish and Chinese.
5. **Speech to speech.** System prompt `Respond with interleaved text and audio.`, reply as text and speech together.
6. **Setting a language.** There is no language parameter. The language is a word in the system prompt, for ASR and TTS.
7. **Tool calling.** Supported, from spoken or written requests. Tools go in through the chat template; with the system prompt `Respond with function calls, and interleaved text and audio.` the model either writes a `<tool_call>` block or answers aloud. Liquid scores it 58.5 on its own tool-calling evaluation (Gemma 4 E4B 72.4, Gemma 4 E2B 55.6, Qwen2.5-Omni 3B 44.3). That is a vendor number on a test we cannot see, so the test in this issue is the first evidence in this repo.

**Exact limits on languages**

- Voice chat (speech in, speech out): "Currently supports English only." Confirmed on the model card.
- Live speech recognition while the caller is still speaking: "currently supports English only." Confirmed on the model card and the audio docs.
- Recorded-turn speech recognition, text to speech and translation: 18 languages. Translation works best into or out of English.
- Not recommended for complex multi-step reasoning or agentic coding.
- Licence: LFM Open License v1.0, free for companies under $10M annual revenue ([licence](https://huggingface.co/LiquidAI/LFM3-Audio-2B/blob/main/LICENSE)), the same terms `docs/08-speech-model-licenses.md` already records for Omni.

Our call cuts a turn at the pause (voice activity), recognises that recording, lets the copilot engine decide, and speaks the reply. That path uses recorded-turn recognition and text to speech, not the English-only live modes. So the languages this stack can speak in a call are the ones recorded-turn recognition and text to speech handle, but only a call test shows which of them work; I will list only those.

**How I plan to build it**

`llama serve` runs as a child of `speech/server.py`, started on the first call that picks `lfm3-audio` (the same lazy loading as Whisper), on a port other than the demo's. `speech/server.py` gets a listener (`Perform ASR in <language>.`) and a voice (`Perform TTS …`) behind the existing `/stt` and `/tts` routes, so the LiveKit adapter in `agent.py` keeps one shape for every stack. Turns end on voice activity alone, as decision 0012 says. LFM3-Audio is also the model behind the engine's `/api/desk` tool calls for this stack, so one model hears, decides and speaks; every fill still goes through decision 0011's code lock in `copilot-engine/src/desk.ts`.

**How the script got here (disclosure)**

The first run of the draft script scored 5 of 8 tool calls and 7 of 10 outcomes. Three of its lines were badly written, not model failures, so I changed them before freezing the script: "Lopes" against "Lopez" sound the same and Parakeet wrote the old name back; a correction that said only "my last name is Gomez" is refused by the desk because "Maria" was not said that turn; and "Okay, go ahead and submit the whole thing" begins with "okay", which the desk counts as a yes, so it filled the date. The same frozen script scored 7 of 8 and 8 of 10 on its second run, with the miss in a different place. So one run is a sample, not a rate: the model's answers at temperature 0 still differ from run to run.

**Worth knowing**

A caller who corrects only a part of a filled answer ("my last name is Gomez") gets the right tool call from the model, but the desk drops it and moves on, saying it will update it. That is the engine's rule that a value must be made of words the caller said, and it is outside this task. It may deserve its own issue.

**A live LiveKit call (observed, one call)**

A separate LiveKit server (the owner's demo was not touched) and a synthetic caller that played recorded speech into the room and answered the agent's two page calls with fixed lines, so the engine was not in the loop and nothing was run in a browser. The agent was `speech/agent.py` on the `lfm3-audio` stack. It greeted in LFM3-Audio's voice, heard both lines correctly ("Hello, my name is Maria Lopez." and the phone number as 555-123-4567), and answered each. The agent's audio, transcribed back, matched the three lines it spoke.

- Recognition took about 1.0 s per turn (3 to 5 s of speech). The voice's first audio came in 0.2 to 0.8 s. From the caller's last word to the first reply sound took 3.6 s and 3.1 s here; that includes the pause that ends a turn and the voice, and the real engine adds its model call on top.
- The model loaded in 11.1 s from cold disk and 3.1 s with the files cached. The agent loads it before the greeting so the first call waits once, not the greeting.
- Memory: the model server used 1.49 GB. The Mac was already swapping when this started (4.4 of 5.1 GB used) and reached 7.2 of 8.2 GB while the model, a second LiveKit server and the agent ran together; the agent logged "VAD inference is slower than realtime" (0.17 to 0.20 s late) twice. So it runs, but with the owner's demo and the other stacks' models loaded it is tight: **memory runs short on this Mac**. Only one stack's models should be loaded at a time for a fair call.
- Noise: the warm-up on 2 s of quiet noise came back as "Thank you." both times, so non-speech audio that gets past the voice-activity check can turn into a made-up turn.

**Languages (the limit)**

The listener and the voice alone work in every language I tried. Each of English, Spanish, French, Italian, Portuguese and Chinese went through the model's own text to speech and back through its speech recognition, and also through a macOS voice into recognition, and came back at 0.94 to 1.00 similarity (the misses were one Italian word, "Buongiorno" heard as "Un giorno", and a Chinese name written with a different character). Hindi is not among the model's 18 languages.

A whole turn does not hold. In Spanish and in French (one scratch turn each, not part of the scripted test) the model called `propose_value` with no arguments, the Spanish read-back came out as "value: María López", and the translated line stopped mid-sentence. That matches the card's "voice chat supports English only". So `stacks.json` lists English for `lfm3-audio` and no more.

A stack with LFM3-Audio's hearing and voice and the LFM3 text model deciding would likely carry those six languages, but it is a different stack from the one the owner chose ("LFM3-Audio end to end"), so I have not built it. It is the owner's call.

**Limits of this evidence**
