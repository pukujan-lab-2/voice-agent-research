# Issue #102: Move the backend's call, rate-limit and cache state into bounded stores, and keep resume snapshots in Octo

- State: open
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/voice-agent-research/issues/102

### Summary

Caller verification (`calls`, `fails`), rate limits (`hits`) and the library cache are in-process maps. They vanish on a restart, two instances can't share them (so a caller could get three tries on each instance), and `calls` only sheds expired entries once it passes 5000, with no hard cap. Resume snapshots have only an in-memory or JSON-file store; the Octo one is still "later".

### Identity and Lineage

Leaf: this issue. Parent: #100. Depends on: none (independent of the prompt budget). Related: #57, decision 0004.

### Acceptance Criteria

- A bounded store (time limit, hard size cap, oldest entry evicted first) behind the existing `Store` interface, plus an atomic counter, backs `calls`, `fails`, `hits`, the cache and the PDF cache.
- An Octo-backed store (workspace SQL table) with a time limit holds resume snapshots, one key per business and session; a second store instance on the same Octo reads what the first wrote, and an expired snapshot is gone.
- Octo's API is checked for a key-value store; anything missing is filed on `Pukujan-lab/octo-database`, not kept as a local copy.
- Tests: size cap and time limit hold under 10,000 inserts; counters survive across two api instances sharing one store; the Octo store runs on a real Postgres engine in the tests.

### Boundaries and Next Action

In scope: `copilot-engine/src/memory.ts`, a new Octo store module, `demo/live-site/api.ts` and its tests. Out of scope: wiring resume into the call UI (#57). Next action: write the bounded store and counter.

### Symptoms

1. **Lost on restart.** Verification locks and rate limits reset.
2. **One instance only.** Each instance counts alone.
3. **No hard cap.** `calls` and `fails` can hold any number of live entries.
