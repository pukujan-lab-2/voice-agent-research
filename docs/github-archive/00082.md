# Issue #82: One automated test suite for every voice config, with audio in Phoenix

- State: closed (2026-11-01)
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/voice-agent-research/issues/82
- Labels: status:resolved

### Summary

The lab's rule is that every voice config is tested so the owner, a business or a visitor can pick one (PROJECT.md rule 8, decision 0012), but no single automated test runs every stack in `speech/stacks.json`. The real-audio tests cover two of the five stacks, the tool-calling test covers two, and nothing measures how well each stack hears and speaks each language it claims. Results don't reach Phoenix with their audio either, so nobody can listen back to a failure.

### Identity and Lineage

Leaf: this issue. Parent: none. Depends on: #71 (lfm3-audio stack and model swap, merged in #77 and #80). Related: #17 (call record), #55 (multilingual), #73, #74, decision 0012, decision 0005 (automated evals).

### Acceptance Criteria

- One command runs every stack in `speech/stacks.json` (or a named subset), one at a time so the speech server swaps models in and out, never all loaded together.
- Per stack and per language it claims: how well it hears real recorded speech (word error rate on PolyAI MINDS-14 phone clips, CC-BY-4.0, where the language is covered; macOS `say` otherwise), how well its voice can be understood (its own speech heard back by Whisper), and time to first audio.
- The tool-calling script from `tests/voice-tools.ts` runs on every stack, not only `english-fast` and `lfm3-audio`.
- Each case is a Phoenix trace through Octo with its scores, and its input and output audio is stored in Octo files and linked from the span, so a failure can be heard.
- The text model can be the Pro's or Windows machine's LFM3 over an SSH tunnel, picked by config.
- A report (JSON and Markdown) lists every stack by language.

### Boundaries and Next Action

In scope: a runner under `demo/live-site/tests/`, the dataset fetch, `tests/voice-tools.ts` widened to every stack, Octo upload and Phoenix spans for test cases. Out of scope: recording live calls' audio (its own issue), new stacks, model comparisons beyond what the suite reports. Next action: build the runner.

### Symptoms

1. **Two of five stacks have real-audio tests.** `tests/voice-call.ts` covers `english-fast`; `tests/voice-languages.ts` covers `english-fast`, `multilingual`, and one English turn each on `parakeet-kokoro` and `whisper-pocket`.
2. **Tool calling tested on two stacks.** `tests/voice-tools.ts` accepts only `english-fast` and `lfm3-audio`.
3. **No per-language hearing or speaking score.** Nothing measures word error rate or voice intelligibility per stack and language.
4. **No audio in Phoenix.** Spans carry transcripts and timings only (Octo's trace read, 2026-11-01).

### Hypotheses (unverified)

- **H1. Every stack can be scored on this 8 GB Mac one at a time.** Status: unverified. Would confirm: a full run completes with swaps between stacks. Would refute: a stack fails to load or the run stalls on memory (Whisper took 26 to 34 s per turn here in #55).

### Counter-signal

Whisper large-v3-turbo was slow on this Mac (#55), so a full run may take long; the Pro may be the better host later.

### Honest Caveat

MINDS-14 has no Hindi, so Hindi uses synthetic speech, which is easier than a real caller. Word error rate on 8 kHz phone audio is harsher than on a browser microphone.

### Problems vs Gaps

Gap: no test covers every config, against the lab's rule that every version is tested.
