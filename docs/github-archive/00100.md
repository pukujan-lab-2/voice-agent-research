# Issue #100: Make the copilot's state bounded: a form of any size, a site of any size

- State: open
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/voice-agent-research/issues/100

### Summary

The owner asked how the copilot holds a call's state and what happens when a site is very large. A business with a 300-field form, or a site with 200 forms, would hit three limits today. The model's prompt lists every field of the form, and a note listing every field and its value is added to every message, so a 300-field form puts hundreds of lines in front of a small model on every turn. The backend keeps caller verification, rate limits and caches in plain in-process maps, so a restart loses them and a second instance can't see them. Each business's copilot config rides along in the page instead of living on the server.

The owner's principle is that our code owns the state and the model never does. This parent makes that hold at scale: the model sees a small, fixed-size window of the form, and everything else lives in code, in bounded stores, and in Octo.

### Acceptance Criteria

- A synthetic 300-field form and a 100-turn call keep the model's prompt under a fixed size, and no collected value is lost or misrouted; the existing tests for small forms pass unchanged.
- Caller verification, rate limits and caches have a time limit and a hard size cap; resume snapshots live in Octo, one key per session and business.
- A business's config (forms, allowed voice stacks) is stored in Octo by business and loaded on demand; one business can never read or change another's state (tested).
- A synthetic site with 200 forms finds the right form by search and loads only that one.
- The limits (fields, turns, concurrent calls) are written down in `docs/` and in PROJECT.md's status; a before-and-after table (prompt size and server memory at 10, 100 and 300 fields; 10 and 1000 concurrent calls) is posted here when done.

### Symptoms

1. **Prompt grows with the form.** `systemPrompt()` prints one line per field and `stateNote()` prints one line per field on every turn; the tool schema also lists every field name.
2. **Server state is process-local.** `calls`, `fails`, `hits`, the 400-entry cache and the PDF cache are `Map`s. `calls` is cleaned only past 5000 entries and only of expired ones, so 5000 live calls grow it without a cap.
3. **Config rides with each request.** The business's pages, forms and voice stacks are sent from the page; the server stores none of it per business.

### Hypotheses (unverified)

- **H1. A window of the current field, the next few and a count of the rest keeps the prompt flat without losing values.** Status: unverified. Would confirm: a 300-field form and a 100-turn call stay under a fixed prompt size with every value intact. Would refute: a value is lost, or filled into the wrong field, when it was said about a field outside the window. Experiment: the synthetic tests in the first child.

### Counter-signal

Today's history cap (6 user turns) already works because code restates the state each turn; the risk is only the form's size, not the call's length.

### Honest Caveat

Nothing here exists yet. The numbers in the final table will come from scripts run in this repository, not from real traffic.

### Problems vs Gaps

Problem: the prompt and the server maps grow without a bound. Gap: no per-business server-side config; no shared store for resume.

### Before and after

The model's prompt: the largest request sent while a whole form is filled (characters of JSON; about 4 characters make a token). `node copilot-engine/tests/scale-report.ts`, test form with a quarter of its fields being 40-option choices.

| Fields | Before | After |
|---|---|---|
| 10 | 9,572 (about 2,400 tokens) | 9,572, unchanged |
| 100 | 37,133 (about 9,300 tokens) | 9,018 (about 2,250 tokens) |
| 300 | 101,072 (about 25,300 tokens) | 9,097 (about 2,270 tokens) |

Server memory held by call state: heap after N calls, each from its own visitor with one failed verification. `node --expose-gc --no-warnings demo/live-site/tests/state-load.ts`. Heap figures from a garbage-collected process move by a few MB between runs, so read them as orders of magnitude.

| Calls | Before | After, in-process store | After, Octo store |
|---|---|---|---|
| 10 | about 0 MB | about 0 MB | none in the process |
| 1,000 | 1.1 MB | 1.1 MB | none in the process |
| 30,000 | 3.1 MB | 2.7 MB | none in the process |
| 100,000 | did not finish: the old cleanup scans every entry per new call past 5,000 | 1.0 MB, capped at 20,000 entries per store | none in the process |

A call costs about 100 bytes, so memory was never the main problem at 1,000 concurrent calls. What changed is that verification locks and resume snapshots survive a restart and are shared by a second instance (tested on a real Postgres engine), and nothing grows without a cap.

### What was built

1. #101 (PR #105): forms over 24 fields show the model a window of at most 14 fields and a count of the rest; a long call's in-memory log and history are capped.
2. #102 (PR #128): `Store` gains an atomic counter; the in-process store has a hard cap; `OctoStore` keeps verification and resume snapshots in Octo; `POST /api/session`. Rate limits stay per instance because an Octo round trip (about 67 ms) is slower than a desk turn can spare.
3. #103 (PR #130): each business's config lives in Octo and loads on demand; `/api/desk` refuses a voice stack the business doesn't allow; two businesses never read each other's state (tested).
4. #104 (PR #131): a site's pages and forms are indexed in Octo and found by search; a 200-form synthetic site finds 30 of 30 requests and loads one flow each.

Limits are in `docs/scaling-limits.md` and `PROJECT.md`; decision 0017 records the rule. Octo has no key-value surface with expiry, so the table is ours; the gap is filed as Pukujan-lab/octo-database#457.
