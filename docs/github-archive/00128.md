# PR #128: Keep call, rate-limit and resume state in stores with a time limit and a size cap

- State: open
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/voice-agent-research/pull/128
- Branch `task/WCP-0041-bounded-state` into `main`, +912 −70 in 19 files

A restart wipes every caller-verification lock, a second instance can't see them, and the maps holding them were capped only by a cleanup that scanned every entry once past 5,000, so the backend couldn't run on more than one machine without letting a caller retry their three tries on each.

## What changes

- The `Store` interface gains `incr`, an atomic counter that expires a fixed time after its first increment. `MemoryStore` gets a hard size cap (expired entries go first, then the oldest written).
- A new `OctoStore` keeps the same interface in one table in the workspace's own Postgres, reached through Octo's SQL surface (decision 0004). The database's clock decides expiry.
- `api.ts` moves `calls`, `fails` and the rate-limit counters onto stores. When live, caller verification and resume snapshots use Octo; rate limits stay in a capped in-process store, because an Octo round trip (about 67 ms) is slower than a desk turn can spare. `STATE_STORE=memory` keeps everything in process.
- New `POST /api/session` saves, reads and deletes a resume snapshot by business and session id (30 minutes, 16 KB, ids checked). Wiring it into the call UI is #57.
- The desk's snapshot key can carry a business, so one business never reads another's.
- Octo has no key-value surface with expiry, so the table is ours; the gap is filed as octo-database#457.
- `docs/scaling-limits.md` records the limits and the measurements.

## Before and after

| | Before | After |
|---|---|---|
| Verification lock after a restart or on a second instance | lost | kept (tested on a real Postgres engine) |
| Entries held by call state | no cap | at most 20,000 per in-process store; none in the process with Octo |
| Heap for 30,000 calls | 3.1 MB | 2.7 MB |

A call costs about 100 bytes, so memory was never large; the change is that the state is shared, survives restarts and has a cap.

## How to verify

## What stays unchanged

Verification rules (3 tries per call, 6 failures per visitor per hour), the 40-a-minute limit, every endpoint's answers, and the widget. The library and PDF caches stay in process: they hold copies of what Octo has.
