# Issue #103: Store each business's copilot config in Octo and load it on demand

- State: open
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/voice-agent-research/issues/103

### Summary

A site's pages, forms and allowed voice stacks live in the page's config and are sent from the page. The server holds none of it per business, so it can't enforce a business's allowed voice stacks, and a large config rides on every request. One business's state must never mix with another's.

### Identity and Lineage

Leaf: this issue. Parent: #100. Depends on: bounded stores (the second child) for the loader's small cache. Related: decision 0012 (voice stacks).

### Acceptance Criteria

- A table in Octo holds one config per business; the server loads one on demand through a small bounded cache.
- `/api/desk` refuses a voice stack the business doesn't allow; resume snapshots are keyed by business.
- The widget can mount with just a business id and take the rest from the server.
- Test: two businesses with the same session id and same form ids never read each other's config or snapshot.

### Boundaries and Next Action

In scope: config loader, the endpoint, a put tool, widget mount, tests. Out of scope: an admin UI. Next action: write the loader and the isolation test.

### Symptoms

1. **Config in every request.** The page carries pages, forms and stacks.
2. **No per-business check on the server.** `stack` is only checked against the two known ids.
