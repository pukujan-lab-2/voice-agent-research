# Issue #107: Make the copilot work on huge sites: search for prose, declared lookups for records

- State: open
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/voice-agent-research/issues/107

### Summary

The owner asked how the copilot gets something to work with on a huge website: search over documents (RAG), a database, or tool calls for both. Today the copilot has one retrieval tool, `answer_question`, over one hand-loaded library (the IRS), and no way to look up a record (an order, an appointment, a price). A business with a 50,000-page site or a product database cannot install it yet: there is no generic way to load its site, the search cannot narrow by section or page type, it gets slow at library size, and the model cannot refine a vague question or look up a fact in a table.

The answer this parent builds: **both, through tool calls that code defines.** Prose (pages, manuals, PDFs) is searched with Octo's hybrid search and the model calls `search_site` or `answer_question`. Records (orders, appointments, prices) are read by declared, read-only lookups that code runs as parameterized SQL on that business's own Octo tables. The model never writes SQL and never sees a field the business did not declare. Octo stays the one store (decision 0004).

### Acceptance Criteria

- One pipeline takes a sitemap or start URL plus HTML, PDF and Markdown documents and loads clean passages with metadata into a business's own Octo prefix; a re-crawl touches only changed pages and removes deleted ones (tested).
- Search narrows by section, page type and language; recall@5/10 and MRR (ranx) and latency are measured on a synthetic 200,000-passage site and on the IRS library, with a figure at each size; whatever is slow in Octo is filed in the Octo repo, not worked around with a local copy.
- The model can call `search_site` (capped per turn, fixed-size results) to refine and combine; quote-only answers and "I don't know" are unchanged.
- A business declares read-only lookups; code runs them with parameters and returns only declared fields; each has a decision-0011 risk score; anything about a person needs caller verification first (tested: injection, cross-business, verified vs not).
- Automated evals (code checks only) pass: citation present, quote word for word in the cited passage, no undeclared field, no cross-business data.
- Limits measured are written in `docs/` and PROJECT.md; a before-and-after table is posted here when done.

### Symptoms

1. **One retrieval tool.** `answer_question` does search, judging and quoting in one call; a vague or two-part question cannot be refined.
2. **No generic load.** The IRS scripts (`irs_*.py`, `lib_*.py`) are one-off; a new business has no way to put its site in.
3. **Slow at size.** A comment in `guide.ts` says the prefix filter is about 15 s of 25 s on 32,000 passages; live traces show a few seconds on 133,000.
4. **No record lookups.** Nothing reads an order, appointment or price from a table.

### Hypotheses (unverified)

- **H1. Putting section, page type and language in the title path and in an Octo table lets search narrow before the limit without a new Octo feature.** Status: unverified. Would confirm: filtered recall matches unfiltered recall on the synthetic site. Would refute: a filter drops gold passages. Experiment: the size test in the second child.
- **H2. Octo's filtered search is the slow part at size.** Status: unverified at 1M. Would confirm: EXPLAIN on a seeded 200k-1M chunk database shows the exact vector scan (octo-database#391). Would refute: filtered and unfiltered take about the same time. Experiment: seed a scratch Octo database and time `octo.match_chunks_hybrid`.

### Counter-signal

None observed yet.

### Honest Caveat

Nothing here exists yet except the pieces named above (`OctoRetriever`, `answer_question`, the IRS scripts, the eval harness). Live ingest into Octo runs about 0.4 s per passage, so a 200,000-passage site cannot be loaded into the live workspace in this work; the size test runs against a scratch Octo database and says so.

### Problems vs Gaps

Gap: no generic ingestion, filters, refine tool or record lookups. Problem: slow filtered search at size (filed upstream).
