# Issue #52: Record the confirmation policy: the model leads, a 1 to 100 risk score sets how it confirms

- State: closed (2026-11-01)
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/voice-agent-research/issues/52
- Labels: status:resolved

### Summary

Decision 0003 has the model make one small JSON choice per turn and code does the rest, including every read-back and confirmation. On 2026-10-31 the owner set a different direction: the model leads the conversation and is guided to read back and confirm according to how much an action matters, on a risk score from 1 to 100. Code still blocks high-risk actions until a recorded yes. This needs a decision that replaces 0003, based on published guidance rather than our own guesses.

### Identity and Lineage

Leaf: this issue. Parent: none. Depends on: none. Related: #16 (model-led desk in the live site, which should build to this policy), #37 (desk v2 read-backs).

### Acceptance Criteria

- A new decision replaces 0003: model-led conversation, the 1 to 100 risk score with its behaviour bands, escalation after a mishearing, a code lock from 56 up, handling for long text such as terms, and asking twice before a high-risk skip or submit.
- It records that the NYC map agent is low stakes and gets no confirmation steps.
- It cites the guides it rests on: Mycroft's confirmation guidelines, the LiveKit prompting guide, and OpenAI's "A practical guide to building agents".
- 0003 is marked replaced and the decisions index is updated.

### Boundaries and Next Action

In scope: `docs/decisions/` only. Out of scope: code changes in the engine or widget; #16 carries those. Next action: write the decision.

### Symptoms

1. **The recorded design disagrees with the owner's direction.** 0003 says code owns read-backs and confirmation; the owner wants the model guided to do them by importance.
2. **No shared scale for importance.** Nothing records how a field or action's stakes set the confirmation it gets, so each agent decides on its own.

### Hypotheses (unverified)

- **H1. A graded risk score lets one policy cover low-stakes lookups and high-stakes submits.** Status: unverified. Would confirm: the desk and the NYC agent both map their actions onto the scale without exceptions. Would refute: actions that need behaviour the bands can't express. Experiment: none planned; the owner asked for no extra test passes.

### Counter-signal

0003's reason still holds in part: small open models are less reliable at open tool use, which is why the code lock stays for high scores.

### Honest Caveat

The band boundaries are a starting point the owner can edit. OpenAI's guide rates tool risk as low, medium or high; the 1 to 100 scale is the owner's finer version of that idea, not something a guide prescribes.

### Problems vs Gaps

Problem: the recorded design is out of date. Gap: no shared risk scale.

### Proposal *(proposal)*

Decision 0011, "The model leads; risk sets how it confirms", replacing 0003. Not written yet.
